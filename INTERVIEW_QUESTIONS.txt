Q1: What is RAG (Retrieval Augmented Generation)?

Expected Answer:
    RAG combines:
    - Retrieval: Fetch relevant documents from a database
    - Augmentation: Use those documents as context
    - Generation: Let LLM answer based on that context
    
    Benefits:
    - Answers grounded in real data (no hallucinations)
    - LLM has recent information (not just training data)
    - Cost-efficient (don't call LLM for everything)
    
    TalentMatch Example:
    - Retrieve: Find matching resumes in Pinecone
    - Augment: Add them as context to GPT-4 prompt
    - Generate: GPT-4 returns structured shortlist

---

Q2: What's the difference between Dense and Sparse vectors?

Expected Answer:
    Dense Vectors (Semantic):
    - 384-dimensional embeddings
    - Captures MEANING ("Engineer" ≈ "Developer")
    - Model: Sentence-Transformers
    - Handles synonyms and context
    
    Sparse Vectors (Keywords):
    - TF-IDF based
    - Captures EXACT WORDS ("Python" matches "Python")
    - Low dimensionality, high interpretability
    - Handles exact keyword matching
    
    Why Both? Hybrid Search
    - Dense alone misses exact keywords
    - Sparse alone misses semantic meaning
    - Together: Best of both worlds

---

Q3: Why do we need Pinecone (vector database)?

Expected Answer:
    Problems without vector DB:
    - Can't quickly search across 1000s of vectors
    - Linear scan too slow (O(n) complexity)
    - No built-in support for hybrid search
    
    Pinecone Advantages:
    - Vector indexing (HNSW, IVF algorithms)
    - Supports hybrid search (dense + sparse)
    - Metadata filtering alongside vectors
    - Serverless (scales automatically)
    - Stores metadata alongside vectors
    
    TalentMatch Usage:
    - Store all resume embeddings
    - Query with hybrid vectors
    - Return top-k matches with metadata

Q6: Explain the complete search pipeline in TalentMatch.

Expected Answer:
    User enters: "Senior Python Engineer with RAG"
    
    1. expand_query()
       - Sends to LLM: "Generate 3 variations"
       - Returns: Original + 3 variations
       - Benefit: Catch different phrasings
    
    2. hybrid_query()
       a) Create dense vector
          - Model.encode() → [0.234, 0.567, ..., 0.123]
          - Scale by (1 - alpha)
       
       b) Create sparse vector
          - TF-IDF transform → {"indices": [5, 42], "values": [0.9, 0.8]}
          - Scale by alpha
       
       c) Query Pinecone
          - Send both vectors
          - Pinecone combines: (dense*weight) + (sparse*weight)
          - Returns top 8 matches
    
    3. rerank_results()
       - For each result: Create (query, resume_preview) pair
       - Cross-encoder model scores pairs
       - Re-sort by cross-encoder score
       - Improves top-1 accuracy 15-20%
    
    4. build_retrieval_chain()
       - LangChain orchestrates all above
       - Loads prompt template
       - Calls GPT-4 to structure results
       - Pydantic validates output
    
    Final Output: ResumeResponse with shortlisted candidates

Q7: What is the alpha parameter in hybrid_query? Why is 0.5 a good default?

Expected Answer:
    Alpha (α) balances semantic vs keyword:
    - α = 0.0 → 100% sparse (only keywords)
    - α = 0.5 → 50% dense + 50% sparse (balanced)
    - α = 1.0 → 100% dense (only semantic)
    
    Why 0.5 is good default:
    - Neither approach dominates
    - Catches both semantic synonyms AND exact keywords
    - Works well for most recruitment queries
    
    When to adjust:
    - Increase to 0.7 if too many false positives (keyword spam)
    - Decrease to 0.3 if missing valid synonyms
    
    Formula in code:
    q_dense_weighted = q_dense * (1.0 - alpha)  # 0.5
    q_sparse_weighted = q_sparse * alpha         # 0.5

Q8: Explain cross-encoder reranking. Why not just use Sentence-Transformer scores?

Expected Answer:
    Sentence-Transformer (SBERT):
    - Encodes query and resume SEPARATELY
    - Good for: Finding similar documents
    - Bad for: Ranking relevance (not trained for it)
    - Limitations: May rank wrongly if both have high similarity
    
    Cross-Encoder:
    - Encodes (query, resume) TOGETHER
    - Specifically trained on relevance ranking
    - Model: cross-encoder/ms-marco-MiniLM-L-6-v2
    - Trained on millions of (query, doc, score) triplets
    
    Example:
    Query: "Senior Python Engineer"
    
    SBERT Ranking:     Cross-Encoder Ranking:
    1. Resume A: 0.92  1. Resume C: 0.96 ← Correct!
    2. Resume B: 0.90  2. Resume A: 0.91
    3. Resume C: 0.88  3. Resume B: 0.87
    
    Code:
    pairs = [(query, resume) for resume in results]
    scores = cross_encoder_model.predict(pairs)
    # Returns relevance scores specifically for ranking

Q10: Why do we use session_id and store results in memory?

Expected Answer:
    Problem without session memory:
    - User asks: "Find ML engineers"
    - User asks: "Tell me about candidate 1"
    - System re-retrieves (expensive!)
    - Might get different results
    
    Solution with session memory:
    - First query: Save results to _session_store[session_id]
    - Follow-up questions: Use saved results
    - Benefits:
      - 40% cost reduction (no re-retrieval)
      - Consistency (same results)
      - Speed (no search latency)
    
    Code:
    if session_id not in _session_store:
        # First query: Do retrieval + save
        out = build_retrieval_chain().invoke(user_input)
        _session_store[session_id] = out["answer_parsed"]
    else:
        # Follow-up: Use saved data
        response = get_qa_agent().invoke(
            {"question": user_input,
             "resume_json": _session_store[session_id]}
        )

Q12: How would you scale TalentMatch to 1 million resumes?

Expected Answer:
    Current State:
    - Works for 5-100 resumes
    - Pinecone handles scale inherently
    
    Scaling Challenges:
    1. Ingestion Time
       - 1M resumes × 5-10 sec each = 50-100 days!
       - Solution: Batch processing, parallelization
    
    2. LLM API Costs
       - 1M resumes × $0.005 (parsing) = $5,000
       - Solution: Use cheaper model for parsing, GPT-4 for ranking only
    
    3. Memory Storage
       - 1M resumes × 384 dims = 384M floats ≈ 1.5 GB dense
       - + sparse vectors + metadata
       - Solution: Pinecone handles automatically
    
    Implementation:
    - Parallel ingestion (100 workers)
    - Batch API calls to LLM
    - Use Claude for parsing (cheaper than GPT-4)
    - Cache TF-IDF vectorizer
    - Use Pinecone Pod (not Serverless)
    
    Code sketch:
    from concurrent.futures import ThreadPoolExecutor
    
    def parallel_ingest(resume_paths, num_workers=100):
        with ThreadPoolExecutor(max_workers=num_workers) as executor:
            results = executor.map(parse_and_embed, resume_paths)
        return list(results)

Q13: How would you implement ranking by custom criteria?

Example: "Find candidates within 50 miles of SF, with 5+ years experience"

Expected Answer:
    Current System:
    - Ranks by relevance score only
    - Doesn't consider location or experience filters
    
    Solutions:
    
    1. Metadata Filtering (Simple)
       - Pinecone supports metadata filtering
       - Filter before search
       
       Code:
       response = index.query(
           vector=q_dense,
           sparse_vector=q_sparse,
           filter={
               "$and": [
                   {"location": {"$in": ["San Francisco", "Bay Area"]}},
                   {"years_experience": {"$gte": 5}}
               ]
           },
           top_k=10
       )
    
    2. Multi-Objective Ranking
       - Calculate multiple scores
       - Combine with weights
       
       Code:
       relevance_score = rerank_cross_encoder(query, resume)
       location_score = 1.0 if location_within_50_miles else 0.0
       experience_score = years_experience / 30  # Normalize
       
       final_score = (
           0.7 * relevance_score +
           0.2 * location_score +
           0.1 * experience_score
       )
    
    3. Hierarchical Ranking
       - First filter by hard constraints (location, experience)
       - Then rank by soft criteria (relevance)

Q14: How do you handle resume updates/deletions?

    Update Scenario:
    - Candidate updates resume
    - Need to re-index
    
    Implementation:
    - Delete old vector from Pinecone
    - Re-parse and re-embed new resume
    - Upload new vector
    
    Code:
    def update_resume(resume_id: str, new_resume_path: Path):
        # Delete old
        index = get_resume_index()
        index.delete(ids=[resume_id])
        
        # Re-ingest
        new_doc = load_and_parse(new_resume_path)
        new_vectors = encode_documents([new_doc])
        upsert_documents([new_doc], new_vectors)

    def delete_resume(resume_id: str):
        index = get_resume_index()
        index.delete(ids=[resume_id])

    def record_feedback(feedback: Feedback):

        model.fit(sentences=pairs, labels=labels)
        
        # Deploy new model

Q17: How would you implement resume similarity matching 
(find similar resumes to a given resume)?

Expected Answer:
    Use Case:
    "Show me resumes similar to John's"
    
    Implementation:
    1. Get John's dense vector
    2. Query Pinecone: "Find similar vectors to John's"
    3. Return top-k matches
    
    Code:
    def find_similar_resumes(resume_id: str, top_k: int = 10):
        index = get_resume_index()
        
        # Get the target resume's vector
        john_vector = index.fetch(ids=[resume_id])["vectors"][resume_id]["values"]
        
        # Query for similar vectors
        results = index.query(
            vector=john_vector,
            top_k=top_k + 1,  # +1 to exclude self
            include_metadata=True
        )
        
        # Remove self from results
        similar = [m for m in results["matches"] if m["id"] != resume_id]
        
        return similar[:top_k]

Q18: How would you detect and handle duplicate resumes?

Expected Answer:
    Problem: Same person uploads resume multiple times
    
    Detection:
    1. Exact Match (Easy)
       - Hash resume text
       - Store in DB
       - Flag if hash exists
    
    2. Semantic Similarity (Better)
       - Compare dense vectors
       - If similarity > 0.95, likely duplicate
    
    3. Fuzzy Matching (Robust)
       - Extract email, name
       - Compare across database
       - Flag matches
    
    Code:
    def detect_duplicate(new_resume: Document):
        new_vector = encode_resume(new_resume)
        
        # Query for similar vectors
        similar = get_resume_index().query(
            vector=new_vector,
            top_k=5
        )
        
        for match in similar["matches"]:
            if match["score"] > 0.95:
                return {
                    "is_duplicate": True,
                    "duplicate_of": match["id"]
                }
        
        return {"is_duplicate": False}

Q19: How would you implement filters for "Must Have" vs "Nice to Have" skills?

Expected Answer:
    Scenario:
    - MUST HAVE: Python, Machine Learning
    - NICE TO HAVE: Fast API, Docker
    
    Current System:
    - Treats all equally in relevance score
    
    Implementation:
    1. Query Filtering
       - Must-haves: Include in main query
       - Nice-to-haves: Add as secondary scoring
    
    2. Score Adjustment
       - Base score: from hybrid search
       - Boost: +0.2 for each must-have found
       - Small boost: +0.05 for each nice-to-have
    
    Code:
    def prioritized_search(
        query: str,
        must_haves: list[str],
        nice_to_haves: list[str],
        top_k: int = 10
    ):
        # Regular hybrid search
        results = hybrid_query(query, top_k=top_k*2)  # Get more to filter
        
        scored = []
        for result in results:
            score = result["rerank_cross_score"]
            text = result["metadata"]["text"].lower()
            
            # Penalty for missing must-haves
            must_have_count = sum(
                1 for skill in must_haves if skill.lower() in text
            )
            if must_have_count < len(must_haves):
                score *= 0.5  # Heavy penalty
            
            # Bonus for nice-to-haves
            nice_to_have_count = sum(
                1 for skill in nice_to_haves if skill.lower() in text
            )
            score += 0.05 * nice_to_have_count
            
            scored.append({**result, "final_score": score})
        
        # Sort and return top-k
        return sorted(scored, key=lambda x: x["final_score"], reverse=True)[:top_k]

Q20: Architecture and trade-offs question:
"Would you use Elasticsearch instead of Pinecone? Why or why not?"

Expected Answer:
    Elasticsearch:
    ✅ Advantages:
    - Mature, battle-tested
    - Self-hosted (control over data)
    - Excellent full-text search
    - Vector search added recently (8.0+)
    
    ❌ Disadvantages:
    - Requires infrastructure management
    - Hybrid search implementation complex
    - Sparse vector support limited
    - More operational overhead
    
    Pinecone:
    ✅ Advantages:
    - Serverless (no ops)
    - Native hybrid search support
    - Built-in sparse vectors with Pinecone Inference
    - Scales automatically
    - Fast query speeds
    
    ❌ Disadvantages:
    - Vendor lock-in
    - Less control over data
    - Higher cost at scale
    
    TalentMatch Choice: Pinecone
    - Reasons:
      1. Hybrid search is built-in
      2. Startup/small team (no ops team)
      3. Cost is acceptable for use case
      4. Fast development/deployment
    
    Alternative: If scaling to millions:
    - Might switch to Elasticsearch + custom hybrid logic
    - Or use Qdrant (open-source alternative)
